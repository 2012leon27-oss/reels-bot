# Архитектура и план системы

## 1. Цель

Система принимает поток мыслей в максимально естественной форме и возвращает
не краткий пересказ, а редактируемый рабочий документ. Главный инвариант:
оригинал никогда не заменяется результатом модели и всегда хранится рядом с ним.

## 2. Пользовательский поток

1. Пользователь открывает обычную HTTPS-страницу или Telegram Mini App.
2. Вставляет текст, записывает голос либо загружает аудиофайл.
3. После распознавания видит транскрипт и может исправить имена или термины.
4. Выбирает формат документа или оставляет автоматический режим.
5. Сервер передаёт модели строгие правила сохранения смысла.
6. Система валидирует JSON-ответ и сохраняет одновременно:
   - оригинальную запись;
   - структурированный документ;
   - решения;
   - задачи с указанными в оригинале владельцами и сроками;
   - идеи, вопросы и теги;
   - переносимый Markdown.
7. Пользователь получает постоянную ссылку, копирует результат или скачивает
   `.md`-файл. Ссылка включается только отдельным действием; оригинал добавляется
   в неё только после явного выбора.

## 3. Компоненты

### Web-клиент

Статический mobile-first интерфейс без сборщика и внешнего UI-фреймворка.
`MediaRecorder` записывает голос; загрузка файла остаётся fallback для
несовместимых браузеров. Все ответы модели вставляются через `textContent`, а
Markdown разбирается безопасным ограниченным рендерером.

### HTTP API

`aiohttp` обслуживает интерфейс и API в одном процессе и одном домене. Это
исключает CORS-конфигурацию и позволяет держать ключ AI только на сервере.
Применяются ограничения размера запроса, частоты AI-операций, типа аудио и
security headers.

### AI-слой

OpenAI-совместимый клиент разделён на две операции:

- структурирование — Groq Llama по умолчанию либо другой провайдер через
  `AI_BASE_URL`/`AI_MODEL`;
- транскрибация — Whisper `whisper-large-v3-turbo` через Groq.

Модель обязана вернуть JSON. Сервер не доверяет форме ответа: убирает
несовместимые значения, нормализует задачи и отклоняет пустой документ.

### Хранилище

Основной production backend — PostgreSQL. SQLite автоматически используется для
локального запуска. Одна запись содержит приватный UUID и независимый
  криптографически случайный `share_id`. Новая заметка приватна по умолчанию.
  История выбирается только по аутентифицированному `owner_id`.

### Telegram

Один процесс параллельно обслуживает web и long polling. Mini App использует
официальную HMAC-проверку `initData`; сообщения и голосовые в чате проходят тот
же pipeline и сохраняются под тем же `telegram:<id>`.

## 4. Модель безопасности

- Ни один API-ключ не попадает в JavaScript или URL.
- Прямой браузерный вход защищён `APP_ACCESS_KEY`.
- Telegram-пользователь определяется только после серверной проверки подписи и
  времени выдачи `initData`.
- Публичная ссылка не раскрывает приватный UUID или владельца.
- В production приложение отказывается принимать приватные запросы, если не
  настроен ни один механизм входа.
- Маленькое аудио держится в памяти, а крупное временно выгружается в системный
  temp-файл; он удаляется сразу после транскрибации.
- Исходник хранится намеренно: это обеспечивает проверяемость результата.
  Поэтому доступ к PostgreSQL и share-ссылкам нужно считать чувствительным.

## 5. Надёжность и отказоустойчивость

- Транскрибация и структурирование разделены: пользователь проверяет текст и не
  теряет запись при ошибке второго шага.
- Черновик текста сохраняется в локальном браузере до успешного результата.
- Неуспешный AI-ответ не создаёт неполную заметку.
- Health endpoint отдельно показывает состояние базы и наличие AI-конфигурации.
- PostgreSQL исключает потерю истории при перезапуске или переносе web service.
- Markdown-экспорт не привязывает данные к конкретной платформе.

## 6. Последовательность реализации

Реализованный базовый production-контур:

1. исправить сломанный entrypoint и объединить Telegram с web service;
2. ввести provider-neutral AI-клиент и строгий контракт результата;
3. добавить Whisper и browser recording;
4. добавить постоянное хранилище, приватную историю и share-страницы;
5. внедрить два способа аутентификации и защитные лимиты;
6. добавить responsive интерфейс, экспорт и Render Blueprint;
7. проверить чистый запуск, контракт данных, auth и HTTP-сценарии.

Следующие усиления, не требуемые для запуска:

- отзыв публичной ссылки и генерация новой;
- роли workspace, команды и разграничение прав;
- редактор результата с сохранением версий;
- поиск по заметкам и семантические связи между ними;
- явная очередь фоновых задач для длинных файлов;
- S3-архив оригинального аудио при осознанном включении;
- optional GitHub sync: запись Markdown в выбранный приватный репозиторий через
  GitHub App. Он не включён по умолчанию, потому что database + share page
  надёжнее для частых записей и не создаёт commit на каждую голосовую заметку;
- метрики качества: ручная отметка потерянных смыслов и повторная обработка
  другой моделью.

## 7. Критерии готовности

- текст и записанный голос проходят end-to-end;
- результат сохраняется и повторно открывается после перезапуска;
- share URL после явного включения открывается без приватного ключа, но не
  раскрывает владельца или исходник без отдельного согласия;
- чужой приватный UUID не читается и не удаляется;
- невалидный Telegram `initData` отклоняется;
- AI key отсутствует в HTML, JS, логах и Git;
- исходник присутствует в базе и экспортированном Markdown;
- интерфейс usable на мобильном экране Telegram.
